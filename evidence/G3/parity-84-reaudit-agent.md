# Draft independent re-audit: all 84 CUDA Z3 parity rows

## 0. Scope, snapshot, and evidence rules

This is a standalone **draft** re-audit of every row in `docs/design/ascend_z3_cost_model_feature_inventory.md` section 6 against the current working tree, not just against `docs/design/cuda_z3_parity_evidence.md`. The audited HEAD is `bb50d8654a3cf65a1caffec57618d9c92b688b6a`; uncommitted owner-ring, cross-stage scalar-Let cloning, and multi-async-producer-stage implementation and tests are included. The older inventory/evidence baseline `4bcc17c4...` is therefore not treated as the current implementation.

No test, build, profiler, or GPU task was run for this re-audit. No source, test, or design document was changed. Conclusions below come from current source/tests and existing logs. In particular, the new host and SM120 artifacts cited below are untracked working-tree evidence, not committed evidence. The current combined SM120 log revalidates the narrow A+B and multi-async subsets; owner-ring numerics have two passing repeat logs. The cross-stage-clone numerical case still fails during compilation, and no arbitrary-workload device conclusion is made.

Status names retain the inventory meanings. `IMPLEMENTED_HOST_TESTED` closes only the explicitly cited host subset; `DEVICE_VALIDATED_SUBSET` closes only the cited device subset. Neither means arbitrary-IR or full Ascend parity. `NOT_APPLICABLE_HARDWARE` means that the named Ascend instruction/ABI/physical resource has no direct CUDA equivalent; it does not close adjacent generic algorithms.

Evidence classes used below:

- **Solver host**: direct Python solver or FFI tests. `evidence/G3/owner-solver-tests-v4.txt` records **54 passed** and includes the newer cross-entry-point lock and cross-process determinism tests.
- **Function-level host IR**: C++/Python pass tests that inspect TIR, metadata, diagnostics, physical versions, barriers, or waits without executing a CUDA kernel. `evidence/G3/parity-host-v9.txt` records **270 passed, 3 deselected**. Focused logs also record clone (`clone-debug-v4.txt`, `clone-debug-diamond-v2.txt`), async (`async-debug-v2.txt`), and owner integration (`owner-integration-debug-v14.txt`) passes.
- **Compile/failure history**: `owner-sm120-v1.txt` failed on missing target capacity; `owner-sm120-v2.txt` compiled depths 1/2/3 but failed the kernel invocation ABI before numerical checks. Those failures are retained, not rewritten as successes. `z3-pipeline-sm120-v1.txt` currently records **1 failed, 2 passed**: A+B and multi-async pass, while the cross-stage Bind clone fails in `PipelinePlanning` because stages 0 and 2 overlap writes to `source`. The clone therefore remains host-only.
- **SM120 numerics/calibration**: `owner-sm120-v3.txt` and `owner-sm120-v4.txt` each record **4 passed**, including exact repeated numerical checks for explicit owner rings at depths 1/2/3. `multi-async-sm120-v1.txt` records **1 passed**, and the combined `z3-pipeline-sm120-v1.txt` revalidates A+B and multi-async exact outputs. G2 calibration artifacts separately record 11 measured microbenchmarks. None of these logs closes arbitrary IR, generic owner inference, or cross-stage-clone numerics.

## 3. Key findings and follow-up implementation gates

1. **Owner ring: restricted implementation with a narrow SM120 numerical subset.** `src/transform/z3_owner_ring_planning.cc` solves two synthetic group tasks, requires declared order 0 -> 1, checks both hand-off inequalities and versions/capacity, and marks a typed WS schedule validated. `src/cuda/transform/materialize_ws_schedule.cc` materializes one ring with two explicit ordered sibling owners and two fixed roles. Host tests cover depth-1/2 counter/parity IR, arrivals, allocation lifetime, depth-1/2/3 aligned capacity totals 48/64/112 bytes, and 14 rejected variants. O3/O4 each pass the host integration case plus all three SM120 depths, with four exact-output checks per depth. This justifies device-subset promotions for Z3-009 and PASS-006/010, **not** for straight-line Z3-005 or automatic PASS-004. Automatic ownership, more owners/roles, nested/guarded/read-first/stage-offset/async epochs, non-CTA-local storage, and mismatched arrivals remain excluded; generic `ZP` still rejects bare owner dependencies.
2. **Cross-stage Let cloning: real host implementation, current device integration failure.** `ZP` iteratively augments the solver problem with consumer-site scalar clones, virtual buffer dependences, stage/order checks, version recomputation, and capacity revalidation. `IP::MaterializeScheduledBindClones` performs fresh-Var construction, input substitution, defs-before-uses placement, and consumer rewriting. Direct chain, diamond, zero-latency, fixed-point-limit, side-effect, inferred-integration, and injection tests justify the Z3-010 host promotion. They do not implement Task/Control trees, arbitrary control-flow Let cloning, or async-producer clone augmentation. In Z1, the new SM120 clone test completes both solver rounds but fails in `PipelinePlanning` because stage 0 and stage 2 overlap writes to `source`; this is a concrete follow-up implementation failure, not a missing optional benchmark.
3. **Multi-async producer stages: host wait proofs plus one SM120 numerical shape.** The previous blanket `A dependency on multiple async stages is not supported` path is replaced for a restricted case. A synchronous consumer can read distinct buffers from different async producer stages; `IP` computes each stage's conservative wait and coalesces with a provable minimum. TI verifies per-consumer waits `[0,2]`, ring depths 4/3, preservation of a four-task Z3 shape, and under-version rejection. TD additionally checks real-solver starts `[1,2,6,8]`, II=2, stages 0/1/3/4, and exact output `5*indices+2`; M1 and Z1 pass. This supports the PASS-008 device-subset promotion. Same-buffer multi-stage writers, TMA/mixed/external async, conditional producers, split/unstable commit groups, and unprovable minima still fail.
4. **Version/capacity behavior improved but is not the Ascend multi-owner merge proof.** `ZP::ValidateSchedule` now recomputes required versions on the augmented problem, rejects under-versioned strict results, and rechecks memory groups instead of silently clamping. This is useful host evidence for Z3-013/016 and PASS-011, but generic multi-owner selected-version merge/max, fixed/non-eligible deductions, register/tmem groups, and final physical placement remain open.
5. **Determinism evidence expanded, but complete-compile determinism remains.** S4 adds cross-entry lock serialization and two-process/two-hash-seed solver equality. Z3-017 stays PARTIAL until repeated complete compilation/generated IR is compared.
6. **Large implementation backlog remains.** While normalization/restoration, recursive Task/Control scheduling, automatic role/owner inference, special-state analysis, PerRole APIs, conflict hints, manual-ring/unlimit/exact-address/region-latency APIs, epoch separating cuts, alias/HB contracts, pre-schedule dual-copy/OOB rewrites, and exact per-version layout/placement are still absent or explicitly blocked. They require implementation, not documentation relabeling.
7. **Documentation drift is visible.** The current `AN::z3_pipeline_annotations` docstring still says scheduled Bind cases requiring cloning remain errors even though current planner/injector code and tests implement the restricted clone path. The old inventory test names `test_stage_order_does_not_bypass_scheduled_bind_validation` and `test_async_same_stage_is_audited_for_manual_schedule_and_rejected_otherwise` no longer exist; this report uses the current replacement tests instead. These drifts are recorded here rather than modifying shared docs.
8. **Device evidence must remain narrowly labeled.** Z1 revalidates only A+B and multi-async and preserves the clone compile failure; O3/O4 validate only the restricted owner-ring depths; calibration supports only measured rates. Earlier owner compile/ABI failures remain in O1/O2 history. Host IR transforms, compile success, measured microbenchmark rates, and numerical kernel results are different evidence planes and must not be merged into a blanket “84 rows closed” claim.
